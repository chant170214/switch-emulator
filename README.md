# Toy Switch-Style Emulator

This repository contains a deliberately compact C++ emulator that mimics a few of the concepts
behind the Nintendo Switch. It is **not** compatible with real Switch software, but it now ships
with an instruction-rich virtual CPU, a small-yet-capable GPU, a text assembler, and an interactive
debugger so you can experiment with your own “homebrew” workloads.

## Highlights

* 32 × 64-bit general purpose registers, stack pointer, link register, integer ALU (add/sub/mul/div,
  shifts, bitwise ops), compare-and-branch family, byte/half/word memory accesses, stack push/pop,
  call/return, software interrupts, and DMA trigger instructions.
* GPU with color and depth buffers, alpha/additive blending, double buffering, line/triangle/rectangle
  drawing, sprite blitting, texture uploads, checksum, and PPM dumping helpers.
* Memory-mapped GPU control window at `0x001F0000` for advanced tinkering (render target select,
  buffer swap, depth clear/toggle, basic command dispatch).
* Text assembler featuring labels, constants (`.equ`/`.macro`), sections, `.org`, `.word`/`.byte`,
  legacy `.data` directives, and recursive `.include` support. Assembled symbols are exported for the
  debugger and CLI.
* Command-line runner with tracing, breakpoints, watchpoints, single-step debugging, optional
  framebuffer dumps, and the ability to package/share Toy Homebrew Binary (`.thb`) and Toy NRO
  (`.nro`) builds.
* Two ready-to-run demos: the built-in showcase and `examples/hello_homebrew.asm` which exercise the
  extended GPU pipeline.

## Building

```sh
cmake -S . -B build
cmake --build build
```

## Automated Smoke Test

Once the project is built you can verify that the emulator, assembler, and Toy NRO packaging
pipeline all function end-to-end by running the bundled CTest target:

```sh
ctest --test-dir build
```

The `emulator_smoke_test` harness assembles `examples/hello_homebrew.asm`, renders it while producing a
PPM dump and ANSI preview, emits a Toy NRO package, and then immediately replays that package to prove
that the generated binaries execute correctly. Artifacts are written to `build/smoke_artifacts/` for
inspection.

## Running & CLI Options

```sh
./build/switch-emulator [program.asm] [options]
```

If no program path is supplied the bundled showcase assembly is executed. Otherwise the emulator will
assemble the provided `.asm` file or, when a packaged binary is detected, load Toy Homebrew Binary
(`.thb`) or Toy NRO (`.nro`) builds generated by this toolchain (see `examples/hello_homebrew.asm`
for a reference workload or `examples/homebrew_template.asm` for a commented starting point).

### Authoring Your Own Toy Homebrew

1. Copy `examples/homebrew_template.asm` to a new file (e.g. `my_program.asm`) and edit the comments
   to customize the drawing commands or logic. The template includes the standard register aliases
   and helper routines most programs need.
2. Build the emulator (`cmake -S . -B build && cmake --build build`).
3. Run your new program via `./build/switch-emulator my_program.asm --show-ansi` or dump a framebuffer
   using `--dump output.ppm`.
4. Prefer piping from editors or generators? Stream source code directly into the emulator using
   standard input:

   ```sh
   cat my_program.asm | ./build/switch-emulator --stdin --show-ansi-mono --show-ansi-width 60
   ```

5. Package the assembled instructions for sharing via `--emit-homebrew my_program.thb` or
   `--emit-nro my_program.nro`, then run them later with `./build/switch-emulator my_program.thb`.

### Viewing the Framebuffer

You now have three ways to inspect the rendered image:

1. Use `--gui` to open a lightweight X11 window that displays the final framebuffer. Close the window
   or press any key while it is focused to return to the CLI. The viewer is intentionally simple so it
   works anywhere X11 libraries are available (desktops, WSL with an X server, etc.).
2. Use `--dump <path>` to write the framebuffer to a `.ppm` file and open it in any image viewer.
3. Use `--show-ansi`/`--show-ansi-mono` (optionally with `--show-ansi-width`) to print a color or
   monochrome ANSI-art preview directly in the terminal once execution halts.

The ANSI/PPM flows continue to work in headless environments (SSH, CI, codespaces, …) where an X11
display is unavailable, while `--gui` gives you an instant OS window when a display server exists.

Supported options:

| Option | Description |
| --- | --- |
| `--dump <path>` | Export the final color framebuffer as an ASCII PPM image. |
| `--debug` | Launch the interactive debugger (single-step REPL). |
| `--trace [path]` | Log executed instructions (stdout by default, or a file via `--trace-file <path>`). Tracing can be toggled from the debugger. |
| `--break <symbol/addr>` | Set an execution breakpoint. Accepts labels, `label+offset`, decimal, or hex addresses. |
| `--watch <spec>` | Log memory reads/writes. Format: `label[:length]` (default length 8 bytes). |
| `--max-steps <N>` | Cap the number of instructions executed during a run/`continue`. Default: 1,000,000. |
| `--package` | Treat the supplied program path as a packaged homebrew even if it does not use the `.thb`/`.nro` extensions. |
| `--emit-homebrew <path>` | After assembling an `.asm` source (or running the built-in demo) emit a shareable `.thb` package to `<path>`. |
| `--emit-nro <path>` | Emit a Toy NRO container (`.nro`) that wraps the assembled instructions/data for sharing with this emulator. |
| `--stdin` | Assemble from standard input instead of an on-disk `.asm` file. Great for piping directly from editors or generators. |
| `--show-ansi` | Print a colorized ANSI-art preview of the framebuffer directly in the terminal. |
| `--show-ansi-mono` | Emit an ANSI preview without color (monochrome ramp). |
| `--show-ansi-width <cols>` | Control the column width of the ANSI preview (default: 80). |
| `--gui` | Open an X11 window displaying the final framebuffer (requires a running X server). |

### FAQ

#### Can this project execute actual Nintendo Switch homebrew?

No. The CPU, GPU, and OS interfaces implemented here are custom learning tools that only understand the
instruction set and runtime documented in this repository. Real Switch binaries target ARMv8 CPUs,
NVN graphics APIs, Horizon OS services, and Tegra X1 peripherals that are **not** emulated. Stick to
the provided assembler/packager flow when authoring “homebrew” for this environment.

#### What happens if I try to load `hbmenu.nro` (or any other `.nro/.nso` binary)?

The emulator now supports **Toy NRO** packages produced via `--emit-nro`, so `.nro` files emitted by this
toolchain run just like `.thb` packages. However, real Switch `.nro/.nso` binaries still will not execute:

1. **Architectural incompatibility.** `.nro/.nso` files are compiled for the Switch’s ARMv8 cores, NVN
   graphics stack, and Horizon OS kernel services. None of those components exist in this teaching
   emulator—the CPU, GPU, memory map, and syscall surface are all custom and intentionally tiny—so the
   instructions in a real homebrew binary simply cannot execute here. Attempting to load `hbmenu.nro`
   will result in an “Invalid Toy NRO magic” error because its binary layout does not match this project’s
   toy container format.
2. **Focused workflow.** The `.asm`/`.thb`/Toy `.nro` flow documented here is guaranteed to work end to
   end. Building your own programs with the bundled assembler or sharing pre-packaged artifacts ensures
   they exercise the teaching CPU/GPU exactly as intended.

Stick to the provided tooling when authoring “homebrew” for this emulator.

#### How do I see what my toy homebrew drew without opening the PPM dump?

Use `--show-ansi` (optionally with `--show-ansi-width` or `--show-ansi-mono`) to print an ANSI-art
preview of the framebuffer directly in the terminal once execution halts. This is handy when testing
programs over SSH or inside CI where graphical viewers are unavailable.

### Debugger Commands

Inside the `--debug` REPL you have access to:

| Command | Effect |
| --- | --- |
| `help` | List available commands. |
| `step` / `s` | Execute one instruction. |
| `continue` / `c` / `run` | Run until a breakpoint, watchpoint hit, or max-step limit. |
| `regs` | Dump all 32 CPU registers. |
| `mem <addr> [len]` | Hex/ASCII memory dump (default length 64 bytes). |
| `break <addr>` | Add a breakpoint during the session. |
| `watch <addr> <len>` | Add a watchpoint during the session. |
| `trace on` | Resume tracing using the last destination (stdout or file). |
| `trace off` | Disable instruction tracing. |
| `trace stdout` | Stream the trace to stdout. |
| `trace file <path>` | Reopen or retarget tracing to a file. |
| `trace status` | Report the current and last-used trace sink. |
| `frame` | Print the current framebuffer checksum. |
| `quit` / `exit` | Leave the debugger. |

## Instruction Set Overview

### Integer/Core Instructions

* `MOVI rd, imm` – Load a signed 21-bit immediate into `rd`.
* `ADDI/SUBI rd, imm` – Add/Subtract signed immediate to/from `rd` in place.
* `ADD/SUB/MUL/DIV rd, rn, rm` – Integer arithmetic.
* `AND/OR/XOR/NOT rd, rn, [rm]` – Bitwise logic (NOT ignores `rm`).
* `SHL/SHR rd, rn, rm` – Logical shifts by the lower 6 bits of `rm`.
* `CMP rn, rm` – Update comparison flags for subsequent conditional branches.
* `BRANCH <label>` – Unconditional PC-relative branch.
* `BRANCHZ/BRANCHNZ rd, <label>` – Conditional branch on zero/non-zero in `rd`.
* `BRANCHGT/BRANCHLT <label>` – Signed comparison against the last `CMP` result.
* `CALL <label>` / `RET` – Call/return using the link register (R30).
* `PUSH rd` / `POP rd` – 64-bit stack operations using R31 as stack pointer.
* `INT rd` – Request a software interrupt using the vector in `rd`. Interrupt handlers are looked up at `0x100 + vector*16`.
* `HALT` – Stop execution.

### Memory Instructions

* `LOAD/STORE rd, rn, imm` – 64-bit load/store at `[rn + imm]`.
* `LOADW/STOREW rd, rn, imm` – 16-bit halfword load/store.
* `LOADB/STOREB rd, rn, imm` – 8-bit byte load/store.
* `DMABLT rd` – Copy a rectangular block into the framebuffer. `rd` points to a descriptor `{src_addr, stride, width, height, dst_x, dst_y}` expressed as 32-bit words.

### GPU Instructions

* `GPUFILL rd` – Fill the active framebuffer with color `rd` (RGBA packed in 0xAARRGGBB).
* `GPUDRAW rd, rn, rm` – Draw a single pixel at `(rd, rn)` with color in `rm`.
* `GPURECT rd` – Draw a filled rectangle. `rd` points to `{x, y, width, height, color}`.
* `GPULINE rd` – Bresenham line using `{x0, y0, x1, y1, color}`.
* `GPUTRI rd` – Filled or wireframe triangle `{x0, y0, x1, y1, x2, y2, color, fill_flag}`.
* `GPUTEX rd, rn` – Upload a texture; `rd` points to `{width, height, pixel_ptr}` (RGBA32). The resulting texture ID is written to `rn`.
* `GPUSPRITE rd` – Blit a textured sprite. `rd` points to `{texture_id, x, y, width, height, flip_x(byte), flip_y(byte)}`.
* `GPUSETTARGET rd` – Select render target index (`0` = front, `1` = back buffer by default).
* `GPUFLIP` – Swap color/depth buffers.

Advanced users can also talk to the GPU via the MMIO window at `0x001F0000`. The registers expose
command/state fields mirroring the internal command queue (see `CPU::GPURegisterState` for the exact
layout).

## Assembler Directives

* `.section code` / `.section data` – Switch between code and data emission contexts.
* `.org <addr>` – Set the current emission address (word-aligned in code, byte-aligned in data).
* `.word <values…>` – Emit 32-bit little-endian values (may reference symbols/constants).
* `.byte <values…>` – Emit individual bytes.
* `.data <addr> <bytes…>` – Legacy shorthand for injecting bytes at an address.
* `.equ name value` / `.macro name value` – Define a symbolic constant.
* `.include "other.asm"` – Recursively assemble another file.
* Labels (e.g. `loop:`) bind to the current code or data address. All resolved symbols are exported
  to the CLI/debugger for use in breakpoints and watchpoints.

## Examples

* `examples/hello_homebrew.asm` – Exercises rectangles, lines, triangles, texture upload, sprites,
  and DMA blits. Assemble/run it with:

  ```sh
  ./build/switch-emulator examples/hello_homebrew.asm --dump hello.ppm
  ```

* `examples/homebrew_template.asm` – Commented scaffold that sets up register aliases, colors, and
  framebuffer helpers so you can immediately start experimenting. Copy it to a new filename and begin
  swapping in your own drawing logic.

* Built-in showcase – Automatically runs when no program is supplied and renders a composite scene
  that touches the texture, sprite, triangle, and DMA paths.

Feel free to extend the instruction set, create additional GPU descriptors, or hook into the MMIO
window for more elaborate experiments. Contributions that add new sample programs or tooling around
this teaching emulator are welcome!

## Toy Homebrew Binary & Toy NRO Workflow

You can distribute assembled programs without shipping their source files by relying on the `.thb`
or Toy `.nro` container formats:

1. Assemble your source and emit both package styles in one step:

   ```sh
   ./build/switch-emulator examples/hello_homebrew.asm \
       --emit-homebrew examples/hello_homebrew.thb \
       --emit-nro examples/hello_homebrew.nro
   ```

2. Run a packaged build directly (auto-detected via extension or `--package`):

   ```sh
   ./build/switch-emulator examples/hello_homebrew.nro --dump hello_from_binary.ppm
   ```

Both containers store the instruction stream, all `.data` patches, and resolved symbols so the
debugger can still reference labels when loading a package.
